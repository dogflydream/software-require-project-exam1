## 1 总体架构设计

### 1.1 技术架构分层

系统采用经典的四层架构，各层与源码文件的对应关系如下：

```
┌───────────────────────────────────────────────────────────────┐
│  UI 展现层（L1）                                                │
│  web/src/** —— Vue 3 单页应用（Vite 构建，产物输出 static/）      │
│  Vue 3 + Vue Router + Pinia + Tailwind CSS                      │
│  视图：市集 / 物品详情 / 商城 / 绿色大屏 / 个人中心 / 资料编辑 /   │
│        公开用户主页 / 后台管理 / 登录 / 注册                      │
│  职责：视图渲染、路由守卫（requiresAuth/requiresAdmin）、          │
│        表单校验（第一层）、Toast 与确认框反馈                      │
│  通信：fetch() 相对路径 /api/**，携带会话 Cookie                  │
├───────────────────────────────────────────────────────────────┤
│  API 控制层（L2）—— main.py                                     │
│  FastAPI 路由函数 + 路由挂载 + 静态文件服务 + SPA 回退路由         │
│  职责：参数解析与第二层校验（Pydantic models.py）、HTTP 状态码、   │
│        身份解析（auth.current_user）、权限校验（require_admin）、  │
│        异常 → 中文 detail 映射                                   │
├───────────────────────────────────────────────────────────────┤
│  业务逻辑层（L3）—— main.py 内业务函数 + database.py 辅助函数     │
│  职责：状态机扭转（_transition）、积分账务（add_points）、         │
│        减碳估算（estimate_carbon / 分类配置缓存）、             │
│        自提码生成（secrets.token_hex）、聚合统计                  │
├───────────────────────────────────────────────────────────────┤
│  SQLite 数据持久层（L4）—— database.py + schema.sql              │
│  职责：连接管理（get_db，row_factory=Row，PRAGMA foreign_keys=ON）、│
│        幂等建表与种子注入（init_db → executescript(schema.sql)）、 │
│        参数化 SQL（? 占位符，防注入）                             │
└───────────────────────────────────────────────────────────────┘
```

**分层调用规约：**

1. L1 仅通过 HTTP + JSON 与 L2 通信，禁止直接访问数据库；
2. L2 路由函数不写裸 SQL 以外的复杂逻辑，多表联动统一交由 L3 辅助函数完成（如 `add_points`）；
3. L3 返回 `sqlite3.Row`，由 L2 统一经 `rows_to_dicts()` 序列化为 dict 后交给 Pydantic 响应模型（FastAPI 无法直接序列化 Row 对象，这是本项目踩坑后的定型约定）；
4. L4 保证同事务原子性：涉及多表写动的操作共享同一 `conn`，最后一次性 `commit()`。

### 1.2 架构决策说明

本项目立项约束为**单日交付、免外部复杂依赖、零构建开箱即用**，选型论证如下：

| 决策点 | 选型 | 论证（为什么不是别的） |
|--------|------|------------------------|
| Web 框架 | **FastAPI** | 内置 Pydantic 请求/响应模型，声明式完成输入校验（枚举、长度、非负），省去手写校验层；自动生成 `/docs` Swagger 文档，QA 可直接在文档页调试接口；异步栈为并发预留空间。对比 Django：免 admin/ORM/模板等重装备，学习与启动成本最低；对比 Flask：省去 blueprint +Marshmallow 拼装。 |
| 数据库 | **SQLite（文件库 campus.db）** | 零安装、零服务进程，Python 标准库内置驱动，`git clone` + `uv sync` 后启动即自动建库建表；单机文件形态完美匹配"数据可随时删除重建"的课堂演示场景。代价是单写者并发上限，实验环境（≤30 并发）内可接受；预留的演进路径见 5.3 节。 |
| 依赖管理 | **uv** | 单一二进制工具，`uv sync` 一条命令按 `uv.lock` 锁定版本精确还原环境（实测 20 包秒级装完）；比 pip + venv 手工流程少 4 条命令且可复现。 |
| 前端 | **Vue 3 + Vite 工程（`web/`），Vue Router + Pinia + Tailwind** | 单文件 + CDN 形态在功能扩张后难以维护（无组件复用、无路由、无状态管理、依赖在线 CDN）；升级为 Vite 工程后可按视图/组件/状态分层，路由懒加载、构建产物输出到 `static/` 仍由 FastAPI 单进程托管，部署形态不变。代价是引入 Node/bun 构建链，仅开发前端时需要（构建产物已提交，运行只需 Python）。 |
| 认证方案 | **服务端会话 + HttpOnly Cookie**，密码 PBKDF2-HMAC-SHA256 加盐哈希 | 早期版本身份取自请求参数 `user_id`，任何调用方传 `user_id=1` 即可读后台数据、看他人订单，属典型越权（IDOR）。改为服务端签发随机会话令牌后，身份由 `auth.current_user` 从 Cookie 推导，客户端传参一律忽略；管理员接口统一 `require_admin` 校验。相比 JWT：服务端会话可即时失效（退出/改密），实现更简单且无需密钥管理。 |
| 部署形态 | **单进程 uvicorn，单机部署** | `uv run uvicorn main:app --reload` 一条命令起服务；`--port` 可随时换端口（8000/9000），前端相对路径请求不受影响。 |

**关键架构权衡记录（ADR 摘要）：**

- ADR-1：响应序列化采用"Row → dict → Pydantic 模型"三步转换，而非返回 ORM 实体——因 SQLite 无官方 ORM 绑定，手工转换层最薄且可控。
- ADR-2：业务规则常量（`REWARD_PUBLISH=10`、`REWARD_CYCLE=20`、`_category_factors`、`ORDER_TRANSITIONS`）集中定义在 `main.py` 顶部而非散落各处，便于需求变更时单点修改。
- ADR-3：种子数据与 DDL 同置于 `schema.sql` 且全部幂等（`IF NOT EXISTS` / `WHERE NOT EXISTS`），使"删库重启 = 恢复演示初始态"成为测试基操。

## 2 数据库逻辑与物理设计

### 2.1 数据库 E-R 实体关系图说明

数据库 `campus.db` 共 **10 张表**：核心业务表 `users` / `items` / `orders` / `point_logs` / `products` / `reports`，以及后续增量补充的 `categories`（分类）、`favorites`（收藏）、`sessions`（会话）、`login_attempts`（登录限流）。下表为核心业务表的关系图：

```
                          ┌──────────────┐
                          │    users     │
                          │──────────────│
                          │ PK id        │
                          │ name         │
                          │ student_no UQ│
                          │ college      │
                          │ role         │
                          │ points       │
                          └──┬───┬───┬───┘
              1:N 发布(owner)│   │1:N 账务│ 1:N 举报人(reporter)
                 ┌───────────┘   │        └────────────┐
                 ▼               ▼                     ▼
        ┌──────────────┐  ┌──────────────┐      ┌──────────────┐
        │    items     │  │  point_logs  │      │   reports    │
        │──────────────│  │──────────────│      │──────────────│
        │ PK id        │  │ PK id        │      │ PK id        │
        │ FK owner_id  │  │ FK user_id   │      │ FK item_id ──┼──► items (1:N)
        │ title        │  │ delta        │      │ FK reporter_id
        │ category     │  │ reason       │      │ reason/status│
        │ status       │  └──────────────┘      └──────────────┘
        │ cycle_count  │
        │ carbon_saved │        ┌──────────────┐
        └──────┬───────┘        │   products   │（独立实体，与 orders 无外键）
               │ 1:N            │──────────────│
               ▼                │ PK id        │
        ┌──────────────┐        │ name         │
        │    orders    │        │ cost_points  │
        │──────────────│        │ stock        │
        │ PK id        │        └──────────────┘
        │ FK item_id   │──► items (1:N，一条订单锁定一件物品)
        │ FK buyer_id  │──► users (1:N)
        │ FK seller_id │──► users (1:N，冗余存储卖家=物品发布者)
        │ pickup_code  │
        └──────────────┘
```

**关系与设计说明：**

1. `users 1:N items`：一个用户可发布多件物品（owner_id 外键）；
2. `users 1:N point_logs`：积分流水只增不改，delta 正负表收支，构成可审计账本；
3. `items 1:N orders`：一件物品在其生命周期内可产生多笔订单（多次流转 → 循环度累加），订单冗余记录 `seller_id`（=下单时物品发布者），即使物品后续易主语义仍自洽；
4. `items 1:N reports`：一件物品可被多次举报；`users 1:N reports`（reporter_id）；
5. `products` 独立无外键，兑换关系通过 `point_logs.reason`（"兑换礼品「××」"）留痕而非建立兑换关联表——实验范围内以账本追溯替代强关联，降低复杂度；
6. `users 1:N sessions`：一个用户可有多个有效会话（多设备登录），退出或改密时删除；
7. `users 1:N favorites` ↔ `items 1:N favorites`：收藏为多对多关系表，`UNIQUE(user_id, item_id)` 防重复；
8. `items.category` 逻辑引用 `categories.name`（未建外键，便于分类重命名时同步更新名称）；
9. `login_attempts` 以登录名为主键，独立于 `users`（未知账号的失败也需计数以防枚举）；
10. 全库启用 `PRAGMA foreign_keys = ON`，外键约束真实生效。

### 2.3 完整的 SQLite DDL 建表 SQL 脚本

以下 DDL 与 `schema.sql` 完全一致（种子 INSERT 语句详见源文件，共 5 用户 + 13 物品 + 4 分类 + 5 礼品 + 1 订单 + 1 举报 + 25 条积分流水，全部带 `WHERE NOT EXISTS` 幂等守卫）：

> 说明：下表为**迁移后的有效结构**。`schema.sql` 中的 `CREATE TABLE` 保留各增量的原始列，
> 后续增量新增的列（如 `users.password_hash`/`avatar`/`bio`、`items.image`/
> `review_status`/`review_note`/`updated_at`）由 `database.py::_migrate()` 通过
> `PRAGMA table_info` 探测后 `ALTER TABLE` 幂等补齐，以兼容已存在的旧库。

```sql
-- ============ 增量 1：用户与物品 ============
CREATE TABLE IF NOT EXISTS users (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL,
    student_no TEXT UNIQUE,
    college TEXT NOT NULL DEFAULT '未填写学院',
    role TEXT NOT NULL DEFAULT 'student',          -- student / admin
    points INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL DEFAULT (datetime('now', 'localtime'))
    -- 增量 6 迁移补充：password_hash, avatar, bio
);

CREATE TABLE IF NOT EXISTS items (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    owner_id INTEGER NOT NULL REFERENCES users(id),
    title TEXT NOT NULL,
    category TEXT NOT NULL,                        -- 分类名称，引用 categories.name
    description TEXT NOT NULL DEFAULT '',
    price REAL NOT NULL DEFAULT 0,
    status TEXT NOT NULL DEFAULT 'available',      -- available / reserved / completed / offshelf
    review_status TEXT NOT NULL DEFAULT 'approved',-- approved / pending / rejected
    review_note TEXT,                              -- 驳回理由（展示给发布者）
    cycle_count INTEGER NOT NULL DEFAULT 0,        -- 循环度：流转次数
    carbon_saved REAL NOT NULL DEFAULT 0,          -- 累计减碳量（kg）
    updated_at TEXT,                               -- 最近修改/审核时间
    created_at TEXT NOT NULL DEFAULT (datetime('now', 'localtime'))
);

-- ============ 增量 8：可管理的物品分类 ============
CREATE TABLE IF NOT EXISTS categories (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL UNIQUE,
    icon TEXT NOT NULL DEFAULT 'box',
    carbon_factor REAL NOT NULL DEFAULT 2.0,       -- 单次流转减碳系数（kg CO₂e）
    sort_order INTEGER NOT NULL DEFAULT 0,
    protected INTEGER NOT NULL DEFAULT 0,          -- 1 = 兜底分类，禁止删除
    created_at TEXT NOT NULL DEFAULT (datetime('now', 'localtime'))
);

-- ============ 增量 2：碳积分流水与兑换礼品 ============
CREATE TABLE IF NOT EXISTS point_logs (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL REFERENCES users(id),
    delta INTEGER NOT NULL,                        -- 正为获得，负为消耗
    reason TEXT NOT NULL,
    created_at TEXT NOT NULL DEFAULT (datetime('now', 'localtime'))
);

CREATE TABLE IF NOT EXISTS products (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL,
    description TEXT NOT NULL DEFAULT '',
    cost_points INTEGER NOT NULL,
    stock INTEGER NOT NULL DEFAULT 0,
    emoji TEXT NOT NULL DEFAULT '🎁'
);

-- ============ 增量 4：订单与线下自提履约 ============
CREATE TABLE IF NOT EXISTS orders (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    item_id INTEGER NOT NULL REFERENCES items(id),
    buyer_id INTEGER NOT NULL REFERENCES users(id),
    seller_id INTEGER NOT NULL REFERENCES users(id),
    status TEXT NOT NULL DEFAULT 'reserved',       -- reserved / confirmed / completed / cancelled
    pickup_code TEXT NOT NULL,                     -- 线下自提码
    created_at TEXT NOT NULL DEFAULT (datetime('now', 'localtime')),
    updated_at TEXT NOT NULL DEFAULT (datetime('now', 'localtime'))
);

-- ============ 增量 5：违规举报与后台审核 ============
CREATE TABLE IF NOT EXISTS reports (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    item_id INTEGER NOT NULL REFERENCES items(id),
    reporter_id INTEGER NOT NULL REFERENCES users(id),
    reason TEXT NOT NULL,
    status TEXT NOT NULL DEFAULT 'open',           -- open / resolved
    created_at TEXT NOT NULL DEFAULT (datetime('now', 'localtime'))
);

-- ============ 增量 6：会话认证 ============
CREATE TABLE IF NOT EXISTS sessions (
    token TEXT PRIMARY KEY,                        -- 随机会话令牌
    user_id INTEGER NOT NULL REFERENCES users(id),
    created_at TEXT NOT NULL DEFAULT (datetime('now', 'localtime')),
    expires_at TEXT NOT NULL
);

-- ============ 增量 6：收藏关注 ============
CREATE TABLE IF NOT EXISTS favorites (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL REFERENCES users(id),
    item_id INTEGER NOT NULL REFERENCES items(id),
    created_at TEXT NOT NULL DEFAULT (datetime('now', 'localtime')),
    UNIQUE (user_id, item_id)
);

-- ============ 增量 12：登录失败限流 ============
CREATE TABLE IF NOT EXISTS login_attempts (
    identifier TEXT PRIMARY KEY,                   -- 登录名（学号/姓名）
    fail_count INTEGER NOT NULL DEFAULT 0,
    locked_until TEXT,                             -- 锁定截止时间，为空表示未锁定
    last_fail_at TEXT NOT NULL DEFAULT (datetime('now', 'localtime'))
);
```

## 3 核心业务流程与状态机设计

### 3.1 物品生命周期状态转移图说明

物品有**两个正交维度**：上架状态 `items.status`（市集可见性与交易阶段）与审核状态
`items.review_status`（内容合规性）。市集展示条件为二者同时满足：
`status IN ('available','reserved') AND review_status = 'approved'`。

**上架状态（`items.status`）与概念编号的映射：**

| 概念编号 | 概念名称 | 代码值 | 进入时机 | 可见性（市集） |
|:---:|----------|--------|----------|:---:|
| 0 | 待审/草稿 | 由 `review_status` 单独表达 | 物主编辑物品后自动转为 `pending`，见下方审核维度 | 不可见 |
| 1 | 上架展示 | `available` | 用户发布物品 / 管理员恢复上架 / 订单取消回滚 | ✅ 可预约 |
| 2 | 已锁定·交易中 | `reserved` | 买家发起预约意向成功 | ✅ 仅展示"已预约"徽章，按钮置灰 |
| 3 | 已完成循环（循环度+1） | `completed` | 订单凭自提码确认完成流转 | ❌ 退出市集，进入统计口径 |
| （补充） | 已下架·违规 | `offshelf` | 管理员执行下架（增量 5） | ❌ 恢复上架后回 `available` |

**审核状态（`items.review_status`）：**

| 代码值 | 含义 | 市集可见 | 进入时机 |
|--------|------|:---:|----------|
| `approved` | 已通过 | ✅ | 发布物品时默认；管理员审核通过 |
| `pending` | 待审核 | ❌ | 物主编辑物品内容后自动转入（增量 9） |
| `rejected` | 已驳回 | ❌ | 管理员驳回并填写理由（理由经 `review_note` 展示给发布者） |

> 待审与已驳回物品仅**物主与管理员**可见（他人访问详情返回 404），避免未审核内容对外暴露；
> 物主修改后需重新审核，防止绕过审核替换物品内容。

**并发与审核约束（实现要点）：**

- 预约采用「条件更新抢占 + 检查影响行数」的原子写法，而非先查后写，
  避免并发预约产生重复订单（超卖）；抢占失败返回 400。
- 仅 `review_status='approved'` 的物品可被预约/收藏，待审与已驳回物品
  虽不在市集展示，也无法通过接口直接下单。
- 订单接口不再返回外部联系方式，双方通过受参与关系校验的订单站内会话沟通。

**状态转移图：**

```
                         发布闲置（POST /api/items）
                                   │
                                   ▼
   恢复上架 ──────┐         ┌──────────────┐
   （管理员）      └────────►│   available  │◄─────┐
                             │   上架展示    │      │ 订单取消
                             └──────┬───────┘      │ （buyer/seller）
                          买家预约    │              │
                          生成自提码  ▼              │
                             ┌──────────────┐      │
                             │   reserved   │──────┤
                             │  已锁定·交易中 │      │
                             └──────┬───────┘      │
                          卖家确认    │              │
                                    ▼              │
                             ┌──────────────┐      │
                             │   confirmed  │──────┘
                             │  待自提       │（订单态，物品仍锁定）
                             └──────┬───────┘
                          凭自提码完成│
                                    ▼
                             ┌──────────────┐
                             │   completed  │──► cycle_count += 1
                             │ 已完成循环     │    carbon_saved += 估算值
                             └──────────────┘    seller.points += 20

   任一非 completed 状态 ──管理员下架──► offshelf ──恢复上架──► available
```

> 注意：`reserved / confirmed` 是**订单状态**，与物品状态联动（订单进入 reserved 时物品同步锁定，取消时回滚 available）。订单侧另有独立状态机 `reserved → confirmed → completed / cancelled`，由 `main.py::_transition()` 强制校验合法边，非法扭转返回 400。

### 3.2 碳积分与循环度算法公式设计

**（1）单次流转减碳量估算（增量 3 定义，增量 4 生效）**

```
carbon_once(category) = estimate_carbon(category)  # 分类表配置缓存，未知分类使用兜底系数
```

| category | 系数（kg CO₂e/次） | 估算依据 |
|----------|:---:|----------|
> 下表为内置分类的默认系数；系数由管理员在「分类管理」中维护，新增分类可自定义。

| 教材 | 2.5 | 纸张生产、印刷与物流环节的 avoided emission |
| 考研 | 2.0 | 纸质资料为主，单册体量小于成套教材 |
| 生活品 | 3.5 | 家电/家具/代步工具类，制造碳足迹更高 |
| 兜底 | 2.0 | 未知类别保守估计 |

**（2）物品级累计指标**

```
item.cycle_count  = item.cycle_count + 1        （每次订单完成 +1）
item.carbon_saved = item.carbon_saved + carbon_once(item.category)
```

**（3）碳积分账务公式**

```
发布闲置:  user.points += REWARD_PUBLISH (10)     —— 增量 2
完成流转:  seller.points += REWARD_CYCLE (20)     —— 增量 4
兑换礼品:  user.points   -= product.cost_points   （前置校验 points >= cost_points 且 stock > 0）
全部变动同步 INSERT INTO point_logs(user_id, delta, reason)，账实分离、可审计
```

**（4）全校聚合指标（GET /api/stats/summary）**

```
total_published = COUNT(items)
total_cycles    = SUM(items.cycle_count)
total_carbon_kg = ROUND(SUM(items.carbon_saved), 2)
total_points    = SUM(users.points)
trees_equivalent = ROUND(total_carbon_kg / 18, 1)    -- 每棵树每年约吸收 18 kg CO₂
```

**（5）排行归一化（学院条形图）**

```
percent(college) = ROUND(carbon_kg(college) / MAX(carbon_kg) * 100)    -- 分母以 1 兜底防除零
```

## 5 软件配置管理与版本回滚方案（重点实验考核项）

### 5.1 Git 分支与标签策略说明

**分支策略**：实验采用**单分支主干模型（main-only）**——每个增量在 main 上完成"编码 → 自测 → 提交 → 打 Tag"闭环后再进入下一增量。理由：单人单日交付场景下，特性分支的合并成本高于收益；Tag 承担基线固化职责后，主干历史即发布历史，简洁且可审计。

**标签策略**：语义化版本 `vMAJOR.MINOR.PATCH-阶段`，与增量一一对应：

```
v0.0.1-init ──► v0.1.0-inc1 ──► v0.2.0-inc2 ──► v0.3.0-inc3 ──► v0.4.0-inc4 ──► v1.0.0-release
  脚手架        市集检索发布      碳积分商城       度量与排行       订单履约         后台合规(正式版)
```

版本号语义：次版本号 = 增量序号；进入 v1.0.0 表示 5 个增量全部验收、进入发布态。**每个 Tag 检出后均为可运行状态**（增量模型交付物定义），这是本配置管理方案的核心质量属性。

**提交信息规范**：Conventional Commits —— `<type>(<scope>): <subject> (<increment 备注>)`，type 限定 chore/feat/docs，scope 标注子系统（init/market/points/metrics/order/admin/srs），subject 英文、末尾括注增量编号，与 SRS 第 5 节需求矩阵双向可查。

## 6 Windows 环境极简部署运行指南

**前置条件**：Windows 10/11；已安装 [uv](https://docs.astral.sh/uv/)（`winget install astral-sh.uv` 或官网安装脚本；本项目实测 uv 0.11.6）。

```powershell
# ① 获取代码（或直接进入已有目录）
cd C:\Users\hxy\Desktop\code\soft-require-project\exam1

# ② 创建虚拟环境（.venv/，指定 Python 3.12；uv 将自动下载所需解释器）
uv venv --python 3.12

# ③ 安装依赖（二选一）
uv sync                          # 推荐：按 uv.lock 精确还原（fastapi、uvicorn[standard]、pydantic）
# 等价手工方式：
uv pip install fastapi "uvicorn[standard]" pydantic

# ④ 启动服务（默认端口 8000；端口被占用可换 9000）
uv run uvicorn main:app --reload
# 或
uv run uvicorn main:app --reload --port 9000

# ⑤ 访问验证
#    前端首页     http://127.0.0.1:9000/          （注意是根路径 /，不是 /index）
#    接口文档     http://127.0.0.1:9000/docs      （Swagger，可直接调试全部 API）
#    健康检查     http://127.0.0.1:9000/api/health
```

**常见问题（Windows 实测记录）：**

| 现象 | 原因与处置 |
|------|------------|
| `uv add/sync` 报 `Failed to update Windows PE resources: 拒绝访问` | 杀毒软件瞬时锁定新写入的 .exe 启动器，**重试 `uv sync` 即可**（实测第二次成功） |
| 访问 `/index`、`/index.html` 得到 404 | 页面仅映射在根路径 `/`，直接打开 `http://127.0.0.1:9000/` |
| 日志出现 `/hybridaction/...`、`/.well-known/...` 404 | 浏览器插件/DevTools 的探测请求，与本系统无关，可忽略 |
| 想重置演示数据 | 停服后删除 `campus.db`，重启即自动重建全部种子数据（建库幂等） |

**部署形态说明**：单进程单机部署，数据库与应用同目录。生产化演进路径（超出实验范围）：uvicorn 换 `--workers N` 多进程 + SQLite 迁移 PostgreSQL + 前端 CDN 资源本地化 + 引入 JWT 认证。

## 7 V2.2.0 实现补充（2026-11-07）

### 7.1 状态一致性与写事务

预约、物主编辑/下架、订单确认/完成/取消、管理员审核/下架/恢复及礼品兑换，在读取业务前置条件前执行 `BEGIN IMMEDIATE`。SQLite 在短写事务中串行化这些操作，`busy_timeout` 控制等待时间。订单转移仍由 `_transition` 校验，并以 `WHERE id=? AND status=?` 条件更新，避免重复奖励。

- 预约同时要求物品 `available` 且审核 `approved`。
- 进行中订单对应物品保持 `reserved`，物主不能改动履约内容；管理员下架/驳回会取消活跃订单。
- 取消只把仍为 `reserved` 的物品改回 `available`，保留已下架状态。
- 已完成物品不能被物主或管理员下架，避免通过恢复上架绕过生命周期。
- 完成时仍验证物品 `reserved + approved`，在一个事务中写订单、循环次数、减碳量、卖家积分与流水。
- 联系方式字段已停用；站内消息在每次读写时校验订单双方身份。

### 7.2 礼品兑换凭证

新增表 `redemptions(id, user_id, product_id, product_name, cost_points, pickup_code, created_at)`，按 `(user_id, id DESC)` 建索引。`product_id` 删除时置空，名称与积分价为兑换时快照，`pickup_code` 为唯一随机凭证。扣积分、减库存、积分流水与凭证插入均在一个事务内。

| 接口 | 身份/输入 | 输出 |
|------|-----------|------|
| `GET /api/redemptions` | 必须登录，身份取 Cookie；忽略客户端 user_id | 仅本人兑换凭证列表，按 id 倒序 |
| `POST /api/redeem` | `{product_id}`，身份取 Cookie | 原有 ok/message/remaining_points，新增 redemption_id 与 pickup_code |
| `GET /api/items/counts?keyword=` | 公开查询，关键词上限 50 字符 | 按类别聚合的数量对象，过滤条件与市集列表一致，无分页截断 |

### 7.3 前端流程与故障恢复

`FulfillDialog` 在发起完成操作前收集人工输入的自提码和线下交接确认。`ProfileView` 提供订单状态筛选、兑换记录与审核意见。`DialogBoundary/useDialogFocus` 统一维护弹窗焦点栈与背景滚动；发布、举报、后台表单、履约确认和全局确认框均挂载到 body，避开页面动画定位影响。

API 客户端在会话失效时发布统一事件，入口脚本清理 Pinia 用户并在受保护页面重定向登录。登录失败不触发该事件。市集按请求序号忽略旧响应，物品详情按路由参数重新读取数据并忽略旧请求。错误页面保留重试入口。

### 7.4 数据升级与验证

新增凭证表使用 `CREATE TABLE IF NOT EXISTS` 自动升级已有数据库，不重置用户数据。种子物品状态仅依据现存进行中订单同步，取消后重启不会再次预约。历史兑换保留原积分流水，不伪造历史凭证。线下凭证暂不含在线核销流程。

运行 `python -m unittest tests_market_regression tests_workflow_regression tests_chat_regression -v`，测试使用临时数据库与上传目录，涵盖计数、图片、重启、重复完成、订单/审核并发、礼品最后库存并发和凭证快照。原认证回归需要另一个隔离服务，不要对正在人工测试的数据库运行。操作指引见《本地测试指南》。


### 自提码最小权限设计修订

`OrderOut.pickup_code` 为可空字段。`order_for_viewer` 在所有订单响应中仅向活跃订单买家保留码；卖家/非参与者/管理员视角以及完成、取消后的响应统一为 null。后台订单列表也经过该过滤。完成接口先强制校验当前用户为 seller_id，再验证手工输入的码，不允许买家用自己的码自确认。

新增 `app_metadata(key, value)` 保存 `pickup_policy` 迁移标记。首次启用本规则时随机替换所有进行中订单曾暴露的旧码，后续启动不会轮换。演示种子也改用随机码。回归覆盖买/卖/后台列表、确认/完成/取消响应、买家携正确码仍被拒、旧码失效和迁移幂等。


## 8 V2.2.0 订单站内沟通实现

`order_messages` 保存 order_id、会话推导的 sender_id、纯文本 content、client_nonce 与时间；唯一键 `(order_id,sender_id,client_nonce)` 保证重试幂等。`order_message_reads` 按 `(order_id,user_id)` 保存已读消息游标，使用 MAX 更新，不能回退。消息按 `(order_id,id)` 建索引，历史默认最近 50 条，支持 before/after，单页上限 100。

四个接口为 `GET /api/conversations`、`GET/POST /api/orders/{id}/messages`、`POST /api/orders/{id}/messages/read`。`conversation_order` 在每次操作中验证订单参与关系；管理员角色不能越权。发送与订单状态更改均使用 `BEGIN IMMEDIATE`，订单结束后停止写入；读取历史仍需参与者身份。发送前校验每分钟 20 条限制，重试已有消息不重复计数。

`MessagesView` 提供会话列表、文本消息气泡、分页、保留草稿与失败重试；以 Vue 文本插值渲染消息，避免把正文解释成 HTML。轮询采用游标增量读取，页面不可见时停止请求，组件卸载时清理定时器。导航每 15 秒刷新未读；会话页每 3 秒刷新。`messages` Pinia store 随账号切换清空，过期请求序号防止跨账号覆盖。

`ProfileUpdate` 拒收 contact，`UserOut/OrderOut` 移除相关响应字段；`my_summary` 用 UserOut 白名单排除内部哈希字段。迁移标记 `contact_retired` 让旧联系方式专用字段只清空一次，兼容已有数据库；新数据库不再创建 contact 列。消息保存于本机数据库，无第三方聊天 SDK。历史报告描述为演进记录，现行行为以本节为准。
