### 1.2 项目背景与建设意义

**项目背景：** 高校每学年毕业季都会产生大量闲置教材、考研资料与生活物品。传统处理方式以废品贱卖或直接丢弃为主，造成两类突出浪费：一是教材的知识价值与物质价值未被充分利用，纸张等资源提前进入回收链；二是宿舍生活用品（台灯、自行车、收纳架等）功能完好却被废弃，重复生产这些商品带来不必要的碳排放。与此同时，在校学生（尤其低年级与考研群体）对低价、可靠的二手教材与物品存在刚性需求，但校园内缺乏一个可信赖、可追溯、有运营激励的流通渠道。

**建设意义：**

1. **资源循环价值**：为校园闲置教材与物品建立线上化、结构化的循环流转通道，通过"循环度"指标量化每件物品的流转次数，延长物品生命周期。
2. **低碳绿色校园倡议**：以"碳积分"体系将发布闲置、完成流转等绿色行为游戏化、可激励，并以"累计减碳量（kg CO₂e）""相当于植树（棵/年）"等数据看板向全校展示环保成效，契合国家"双碳"战略与绿色校园建设要求。
3. **教学实验价值**：本项目作为软件工程/软件项目管理实验项目，完整实践**增量模型**开发与**软件配置管理（SCM）**：每个增量交付即可运行的版本，并按 Conventional Commits 规范提交、以 Tag 固化基线，支持 `git checkout` 随时回滚演示。

### 1.3 核心业务术语定义

| 术语 | 英文/标识 | 定义 |
|------|-----------|------|
| **循环度** | cycle_count | 单件物品自上线以来被成功"确认完成流转"的累计次数（`items.cycle_count`）。每完成一次订单履约（买家验货自提后确认），循环度 +1。循环度是衡量单件物品重复利用效率的核心指标；全校循环度为所有物品循环度之和（`total_cycles`）。 |
| **碳积分** | points | 平台发放给用户的虚拟激励积分（`users.points`），获取途径：发布一件闲置 +10 分；卖家每完成一次流转 +20 分。消耗途径：积分商城兑换礼品（扣减对应 cost_points）。全部增减均写入积分流水表 `point_logs`（delta 正负记录），可审计追溯。 |
| **减碳量估算** | carbon_saved | 单次流转的减碳量按物品类别估算：教材 2.5 kg、考研资料 2.0 kg、生活品 3.5 kg（CO₂e，定义于 `CARBON_FACTOR`）。物品的 `carbon_saved` 为其历次流转估算值累加。全校累计减碳量同时换算"相当于植树（棵/年）"，换算系数为 18 kg CO₂/棵·年。 |
| **增量式交付** | Incremental Delivery | 将系统划分为 5 个功能增量（市集 → 碳积分 → 度量分析 → 订单履约 → 后台审核），每个增量开发完成后立即测试并提交 Git、打 Tag 固化为基线，保证任意标签检出后均为可运行状态。 |
| **线下履约（自提码）** | pickup_code | 买卖双方线下验货交易后，凭系统生成的自提码（格式 `GC-XXXXXX`，如种子数据 `GC-2026-0001`）在系统中确认完成流转；自提码错误将拒绝完成操作，防止虚假确认。 |
| **违规举报** | report | 用户对疑似违规物品（描述失实、违禁品等）提交的举报记录，进入管理员待处理队列（open），处理后标记 resolved。 |
| **状态机扭转** | State Transition | 订单生命周期受状态机约束：`reserved → confirmed → completed`，`reserved/confirmed → cancelled`；非法扭转（如对已完成订单再次确认）返回 400 并给出中文原因。 |

## 2 任务概述与角色建模

### 2.1 系统总体用例图（文本形式表述）

**参与者（Actor）：**

| 参与者 | 说明 | 典型代表（种子账号） |
|--------|------|----------------------|
| 学生买家 | 浏览/检索市集物品，对心仪物品发起预约意向，线下自提后确认完成流转，可举报违规物品，可兑换碳积分礼品 | 李循环、王低碳、赵再利用 |
| 学生卖家 | 发布闲置物品，管理自己物品的订单（确认预约、完成流转、取消），赚取碳积分 | 张绿循 |
| 系统管理员 | 进入后台管理：物品下架/恢复上架、查看与处理违规举报、查看平台全局汇总数据 | 管理员老师（role=admin） |

> 说明：任一学生账号可同时扮演买家与卖家两种角色（同一用户既可发布物品也可预约他人物品）；系统通过前端"当前身份"选择器确定操作主体，管理员操作在后端进行角色校验（role != admin 返回 403）。

**用例图（文本形式）：**

```
                        ┌──────────────────────────────────────────────┐
                        │               绿循校园系统                     │
                        │                                              │
   学生买家 ────────────┤  UC1 浏览/检索闲置物品（分类筛选、关键词搜索）   │
     │                  │  UC2 发布闲置物品（+碳积分）                   │
     │                  │  UC3 发起预约意向（生成自提码）                │
     ├──(可兼任卖家)─────┤  UC4 确认预约意向（卖家）                      │

     │                  │  UC6 取消订单                                 │
     │                  │  UC7 查看碳积分流水 / 个人中心                  │
     │                  │  UC8 兑换积分商城礼品                          │
     │                  │  UC9 举报违规物品                              │

     │                  │                                              │
   系统管理员 ───────────┤  UC11 物品下架 / 恢复上架                      │
     │                  │  UC12 查看与处理违规举报                       │
     │                  │  UC13 查看平台全局汇总数据大屏                  │
                        └──────────────────────────────────────────────┘
```

**主要业务流程（概要级）：**

1. **发布流转**：卖家发布闲置（+10 积分）→ 物品进入市集（available）→ 买家发起预约（available→reserved，生成自提码）→ 卖家确认预约（reserved→confirmed）→ 双方线下验货自提 → 任一方凭自提码确认完成（confirmed→completed，物品循环度+1、卖家+20 积分、减碳量累加）。
2. **合规治理**：用户举报 → 管理员核实 → 可下架物品（offshelf，市集不可见）→ 处理完毕恢复上架或标记举报已解决。
3. **积分闭环**：绿色行为赚积分 → 商城兑换礼品扣积分并减库存 → 流水全程可查。

### 2.2 系统运行环境、软硬件约束与数据持久化要求

**运行环境：**

| 类别 | 要求 |
|------|------|
| 操作系统 | Windows 10/11（本项目实测 Windows 10.0.19045 x64）；兼容 Linux/macOS（纯 Python 栈，无平台耦合） |
| Python 运行时 | Python ≥ 3.12（依赖管理使用 uv，虚拟环境位于 `.venv/`） |
| 核心依赖 | fastapi 0.141.x、uvicorn[standard] 0.54.x、pydantic 2.13.x、sqlite3（标准库内置） |
| 前端依赖 | Vue 3 + Vite + Vue Router + Pinia + Tailwind CSS（工程位于 `web/`，用 bun 构建）；构建产物输出到 `static/` 并由 FastAPI 托管，**运行环境无需 Node**，仅开发前端时需要 |
| 浏览器 | Chrome / Edge / Firefox 现代版本（需支持 ES2020 与 CSS Grid） |
| 默认服务地址 | `http://127.0.0.1:8000/`（可通过 `--port` 参数调整，如 9000）；Swagger 文档 `/docs` |

**软硬件约束：**

1. 单机部署形态：FastAPI 应用与 SQLite 数据库文件同机，适合课程实验与课堂演示，不要求独立数据库服务器。
2. 启动端口被占用时 uvicorn 报错退出，需更换端口重试。
3. 前端依赖已工程化并本地构建，产物随仓库提交，**离线环境可正常使用**（无需 CDN）。

**数据持久化要求：**

| 要求 | 说明 |
|------|------|
| 自动建库建表 | 服务启动时（startup 事件）执行 `init_db()`：若 `campus.db` 不存在则自动创建，并执行 `schema.sql` 建立全部 6 张表（users、items、point_logs、products、orders、reports）。建表语句均为 `CREATE TABLE IF NOT EXISTS`，种子数据均带 `WHERE NOT EXISTS` 守卫，**重复启动幂等，不产生脏数据**。 |
| 种子数据 | 5 个用户（含 1 名管理员）、13 件物品（含 5 件已完成流转的历史物品用于排行榜演示）、5 件商城礼品、1 条已确认待自提订单（自提码 GC-2026-0001）、1 条待处理举报。 |
| 事务要求 | 涉及多表写动的操作（发布物品+积分流水、完成流转+循环度+减碳量+积分、兑换+扣分+减库存）须在同一事务中提交；`get_db()` 连接开启 `PRAGMA foreign_keys = ON` 保证外键约束。 |
| 备份与删除 | `campus.db` 属可再生产物（已列入 `.gitignore`），删除后重启服务即可恢复到种子数据状态，便于测试环境重置。 |

## 3 五个增量模块功能规格说明

> 每个增量交付即包含"业务规则 → 输入数据 → 处理逻辑 → 输出结果 → 异常处理"完整规格，与源码实现一一对应。

### 3.1 增量 1：闲置教材市集检索与发布子系统（v0.1.0-inc1）

**功能概述**：提供闲置物品的列表展示、分类筛选、关键词检索与发布上架能力，是全系统的业务入口。

**数据实体**：`users`（id, name, student_no, college, role, points, created_at）、`items`（id, owner_id, title, category, description, price, status, cycle_count, carbon_saved, created_at）。

| 项目 | 规格 |
|------|------|
| **业务规则** | BR1-1 物品分类仅限三类：教材 / 考研 / 生活品（服务端 Pydantic 正则校验 `^(教材\|考研\|生活品)$`）。BR1-2 物品状态初始为 available；市集仅展示 available 与 reserved 两种状态（completed / offshelf 不对外可见）。BR1-3 发布者必须为已存在用户。BR1-4 标题 1–100 字符，描述 ≤500 字符，价格 ≥0。BR1-5 列表按创建时间倒序排列。 |
| **输入数据** | ① `GET /api/items?category=&keyword=`：category（可选，枚举三类）、keyword（可选，模糊匹配标题与描述）；② `POST /api/items`：owner_id(int)、title(str)、category(枚举)、description(str)、price(float)。 |
| **处理逻辑** | 检索：JOIN users 取发布者姓名与学院，按条件拼接 WHERE 子句（LIKE '%kw%'）后按时间倒序返回。发布：校验 owner 存在 → INSERT items（status=available, cycle_count=0, carbon_saved=0）→ 返回带发布者信息的新记录。 |
| **输出结果** | 检索返回物品数组（含 owner_name、owner_college、循环度徽标数据）；发布返回 201 + 完整物品 JSON；页面以卡片网格呈现，含分类徽章、状态徽章与"＋发布闲置"弹窗表单。 |
| **异常处理** | ① owner_id 不存在 → 404「用户不存在」；② category 非法 → 422 Pydantic 校验错误；③ title 为空/超长 → 422；④ 检索无结果 → 返回空数组，前端显示"暂无符合条件的闲置物品"空态。 |
| **验收要点** | 8 条种子物品可全部列出；category=考研 精确返回 2 条；keyword=台灯 返回"小米台灯 Pro"；发布后新物品立即可见且状态为 available。 |

### 3.2 增量 2：绿色碳积分与商城置换子系统（v0.2.0-inc2）

**功能概述**：建立"绿色行为 → 碳积分 → 礼品兑换"的激励闭环，包含积分发放、流水审计与积分商城。

**数据实体**：`point_logs`（id, user_id, delta, reason, created_at）、`products`（id, name, description, cost_points, stock, emoji）。

| 项目 | 规格 |
|------|------|
| **业务规则** | BR2-1 发布一件闲置奖励 +10 碳积分（常量 `REWARD_PUBLISH=10`）。BR2-2 每笔积分变动必须同时写入 point_logs，reason 需可读（如"发布闲置《××》获得碳积分"/"兑换礼品「××」"）。BR2-3 兑换前提：用户积分 ≥ 礼品 cost_points 且库存 >0。BR2-4 兑换成功后积分扣减、库存 -1，两者同事务完成。BR2-5 积分可为负余额？否——兑换前预校验保证不透支。 |
| **输入数据** | ① `GET /api/point-logs?user_id=`：用户 id；② `GET /api/products`：无参数；③ `POST /api/redeem`：user_id(int)、product_id(int)。 |
| **处理逻辑** | 发布物品后在同一事务中调用 `add_points(conn, user_id, +10, reason)`（UPDATE users.points + INSERT point_logs）。兑换：校验用户/礼品存在 → 校验库存与积分 → add_points(-cost) → UPDATE products.stock-1 → 提交，返回剩余积分。 |
| **输出结果** | 兑换返回 `{ok, message, remaining_points}`，message 形如"成功兑换「食堂 5 元代金券」，请到学生会办公室领取"；前端商城 Tab 展示礼品卡（积分价、库存、兑换按钮置灰逻辑），个人中心展示积分余额与流水列表（正分绿色/负分红色）。 |
| **异常处理** | ① 用户或礼品不存在 → 404「用户或礼品不存在」；② 库存不足 → 400「礼品库存不足」（按钮同时置灰"已兑完"）；③ 积分不足 → 400「碳积分不足，还差 N 分」；④ 前端发布成功后同步刷新用户积分与流水，保证三端数据一致。 |
| **验收要点** | 积分 120 的用户发布物品后变为 130；兑换 60 分礼品后剩余 70 且库存 50→49；积分不足兑换 200 分礼品返回"还差 130 分"；流水按时间倒序完整记录 +10/-60 两笔。 |

### 3.3 增量 3：物品循环度度量与低碳数据分析子系统（v0.3.0-inc3）

**功能概述**：定义并计算核心环保指标（循环度、累计减碳量），提供全校环保汇总、环保先锋榜、学院减碳排行三类数据接口与前端"绿色循环大屏"。

**业务规则（核心指标算法）**：

- BR3-1 单次流转减碳估算系数（`CARBON_FACTOR`）：教材 2.5 kg、考研资料 2.0 kg、生活品 3.5 kg CO₂e；未知类别兜底 2.0 kg。
- BR3-2 物品累计减碳量 `carbon_saved` = 历次流转估算值之和；循环度 `cycle_count` = 完成流转次数（两者在增量 4 的完成流转动作中联动更新）。
- BR3-3 全校汇总：total_published（物品总数）、total_cycles（Σ循环度）、total_carbon_kg（Σ减碳量，保留 2 位小数）、total_users、total_points（Σ用户积分）、trees_equivalent = total_carbon_kg / 18（每棵树每年约吸收 18 kg CO₂，保留 1 位小数）。
- BR3-4 环保先锋榜：按个人名下物品 Σcarbon_saved 降序，其次按 Σcycles、再按积分排序，默认 Top 10。
- BR3-5 学院排行：按学院聚合减碳量降序，并计算 percent（相对榜首的百分比，用于前端条形图宽度）。

| 项目 | 规格 |
|------|------|
| **输入数据** | ① `GET /api/stats/summary`：无；② `GET /api/rank/users?limit=10`：limit 可选；③ `GET /api/rank/colleges`：无。均为只读聚合查询。 |
| **处理逻辑** | 三条 SQL 聚合：SUM/COUNT + LEFT JOIN items ON owner_id；学院排行对首榜计算归一化百分比。种子数据中 5 件已完成流转物品保证排行榜非空可演示。 |
| **输出结果** | 前端"排行榜"Tab：顶部 5 张指标卡（累计减碳/累计循环/上线物品/参与师生/相当于植树）；左栏先锋榜（前三名金银铜牌样式，含循环次数与积分）；右栏学院条形排行（渐变进度条 + 成员数与流转次数）。切换到该 Tab 时自动刷新数据。 |

### 3.4 增量 4：意向预约与线下履约流转子系统（v0.4.0-inc4）

**功能概述**：实现从"买家发起预约意向"到"线下验货自提、确认完成流转"的完整订单生命周期，含状态机扭转、自提码校验、循环度与积分联动。

**数据实体**：`orders`（id, item_id, buyer_id, seller_id, status, pickup_code, created_at, updated_at）。

**订单状态机**：

```
                    ┌─────────────┐  卖家确认   ┌─────────────┐  凭自提码完成  ┌───────────┐
 买家预约（生成码）→ │ reserved    │ ─────────→ │ confirmed   │ ───────────→  │ completed │
                    │ 已预约       │            │ 待自提       │               │ 已完成     │
                    └──────┬──────┘            └──────┬──────┘               └───────────┘
                           │ 买家/卖家取消             │ 买家/卖家取消
                           ▼                          ▼
                      ┌─────────────┐
                      │ cancelled   │（物品状态回滚 available）
                      │ 已取消       │
                      └─────────────┘
  非法扭转（如 completed→confirmed、reserved→completed）一律 400 拒绝。
```

| 项目 | 规格 |
|------|------|
| **业务规则** | BR4-1 仅 available 物品可被预约，预约后物品状态转 reserved；拥有进行中订单（reserved/confirmed）的物品不可重复预约。BR4-2 不能预约自己发布的物品。BR4-3 仅卖家可执行"确认预约"（403 校验）。BR4-4 完成流转需自提码精确匹配（买家或卖家任一方发起均可）。BR4-5 完成流转在同一事务中：订单→completed、物品→completed 且 cycle_count+1、carbon_saved+估算值、卖家+20 积分（`REWARD_CYCLE=20`）并写流水。BR4-6 取消订单将物品回滚为 available。BR4-7 状态扭转仅允许 `reserved→{confirmed,cancelled}`、`confirmed→{completed,cancelled}`（`ORDER_TRANSITIONS`）。 |
| **输入数据** | ① `POST /api/orders`：item_id、buyer_id；② `GET /api/orders?user_id=`：返回该用户作为买家或卖家的全部订单；③ `POST /api/orders/{id}/confirm | complete | cancel`：user_id，complete 额外要求 pickup_code。 |
| **处理逻辑** | 预约：校验物品存在/非自购/available → 生成自提码 `GC-` + 6 位随机十六进制大写（secrets.token_hex(3).upper()）→ INSERT order(reserved) + UPDATE item(reserved)。确认：`_transition()` 统一校验当前状态与目标状态合法性后 UPDATE。完成：校验参与方与自提码 → 状态扭转 → 联动更新物品与积分。 |
| **输出结果** | 全部订单接口返回 `OrderOut`（含 item_title、buyer_name、seller_name、price、pickup_code、status）。前端：市集卡片"预约意向"按钮预约成功后 toast 展示自提码；个人中心"我的循环订单"分"我买到的/我卖出的"两个视图，展示状态徽章（已预约黄/待自提蓝/已完成绿/已取消灰）、自提码与操作按钮（卖家：确认预约；双方：完成流转、取消）。 |
| **异常处理** | ① 物品不存在 → 404；② 预约自己物品 → 400「不能预约自己发布的物品」；③ 物品不可预约 → 400「该物品当前不可预约」；④ 非卖家确认 → 403「只有卖家可以确认预约」；⑤ 自提码错误 → 400「自提码不正确」；⑥ 非参与方操作 → 403；⑦ 非法状态扭转 → 400「订单状态为「待自提」，不能执行该操作」等中文提示。 |
| **验收要点** | 端到端实测：预约→买家确认被拒(403)→卖家确认→错码完成被拒(400)→正确码完成→物品 cycle_count=1、carbon_saved=2.5（教材）、卖家积分 120→140；取消流程后物品回 available；对 confirmed 订单执行 confirm 返回 400。种子订单 GC-2026-0001（买家王低碳/卖家张绿循）可直接演示待自提环节。 |

### 3.5 增量 5：平台合规审核与后台运维大屏子系统（v1.0.0-release）

**功能概述**：面向管理员的后台：物品下架/恢复上架、违规举报受理与处理、平台全局汇总数据卡片；面向普通用户开放举报入口。

**数据实体**：`reports`（id, item_id, reporter_id, reason, status, created_at）。

| 项目 | 规格 |
|------|------|
| **业务规则** | BR5-1 全部 /api/admin/* 接口进行管理员角色校验（`_require_admin`：user 存在且 role=admin，否则 403「需要管理员权限」）。BR5-2 下架物品状态转 offshelf，市集立即不可见；已完成（completed）物品不提供下架按钮。BR5-3 仅 offshelf 物品可恢复上架，恢复后状态回 available。BR5-4 举报理由 2–200 字符；举报状态 open→resolved 单向，重复处理返回 400。BR5-5 管理员物品清单按未处理举报数降序排列，便于风险优先处置。 |
| **输入数据** | ① `POST /api/reports`：item_id、reporter_id、reason；② `GET /api/admin/summary | admin/items | admin/reports?user_id=`：均需管理员 user_id；③ `POST /api/admin/items/{id}/offshelf | restore`、`POST /api/admin/reports/{id}/resolve`：user_id。 |
| **处理逻辑** | admin/summary 复用增量 3 的 stats_summary 并叠加订单统计（总数/已完成/进行中）、待处理举报数、被举报物品数；admin/items 用子查询为每件物品附加未处理举报数 report_count；下架/恢复/处理举报均为先权限校验、再状态校验、后 UPDATE 的三段式处理。 |
| **输出结果** | 后台 Tab：非管理员显示"管理员专属区域"引导卡；管理员可见 4 张汇总卡（订单总数/进行中订单/待处理举报（红色高亮）/全校累计减碳）、物品审核表格（含状态徽章、⚠ 举报数徽章、下架/恢复按钮）与举报处理列表（理由、举报人、时间、标记已处理按钮）。市集物品卡对非本人物品提供 ⚠ 举报按钮（prompt 填写理由）。 |
| **异常处理** | ① 非管理员 → 403「需要管理员权限」；② 物品/举报不存在 → 404；③ 重复下架 → 400「物品已是下架状态」；④ 非下架物品恢复 → 400「仅下架物品可恢复上架」；⑤ 重复处理举报 → 400「该举报已处理」；⑥ 举报理由 <2 字 → 前端拦截不提交。 |
| **验收要点** | 学生账号访问 admin/summary 返回 403；管理员可见种子举报（置物收纳架，1 条 open）；下架后 /api/items 不再返回该物品；恢复上架后重新可见；处理举报后 open_reports 递减。 |

- **正向追踪（需求 → 实现）**：每条需求编号在源码中对应明确的函数/端点（如 REQ-ORD-03 → `main.py::complete_order`），在数据库中对应明确字段（如 REQ-MET-01 → `items.cycle_count`）。

- **变更控制约定**：后续任何需求变更须在本矩阵追加新编号（不得修改历史编号语义），并以新的 Conventional Commit（`feat:`/`fix:`）提交、按需打新 Tag，保证矩阵与仓库历史持续一致。
